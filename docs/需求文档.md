版本：0.1（需求初稿）

> **实现状态（2026-11-19）**：需求已在 App 1.1.0 中落地——星铁 4.7.0（4 个切换文件）、原神 7.2.0（3 个）、绝区零 3.3.0（3 个）均完成真机双向切换验证；快照加密、历史回滚、账号密码备注、分栏记忆、正式签名与 GitHub Release 均已完成。功能与验收细节见 [App 说明](app/账号切换App原型.md)，本文保留产品需求原文。

## 1. 项目目标

制作一款运行在已取得 Root 权限的安卓手机上的独立 App，管理本机米哈游游戏的多个账号状态，并在同一游戏客户端中切换账号，减少重复输入账号信息的操作。

核心流程：识别已安装游戏 → 记录当前登录状态及关联位置、文件 → 研究并验证游戏自身的账号切换机制 → 实现对应适配 → 保存多个账号状态 → 选择账号并切换 → 启动游戏验证。

本项目是“账号登录状态管理与切换工具”，不是游戏数据包切换器、服务器转换器或游戏资源共享工具。

## 2. 范围与边界

### 2.1 首期支持

| 游戏 | 地区范围 | 首期验收目标 |
| --- | --- | --- |
| 原神 | 中国大陆版本 | 账号状态记录、保存、切换、备注、编辑、删除 |
| 崩坏：星穹铁道（简称星铁） | 中国大陆版本 | 同上 |
| 绝区零 | 中国大陆版本 | 同上 |

- 三款游戏均为首期正式交付要求，不以完成一款代替全部完成。
- 中国大陆官方客户端为首轮验证对象。中国大陆渠道服单独识别、单独记录兼容性；具体渠道支持清单待确认，不默认与官方客户端兼容。
- 不包含国际服、云游戏客户端、PC 客户端及跨设备账号迁移。
- 同一游戏的不同包名、签名或渠道不得混用账号快照。
- 不修改角色、资产、服务器账号绑定或游戏资源内容。
- 不承诺绕过验证码、实名要求、设备验证、会话失效或服务端风控；出现这些情况时引导用户完成游戏原有验证。

### 2.2 产品原则

1. 先确认机制，再编写切换适配；未验证的路径和字段不作为事实固化。
2. 优先模仿游戏原有切换流程及其必要的本地状态变化，不预设“替换一个文件即可完成”。
3. 只操作经验证与切换有关的最小数据集合，避免备份或覆盖整个游戏目录。
4. 凭据与账号快照默认只存本机，不上传账号信息。
5. 每次破坏性状态变更都应有前置检查、确认、备份及失败处理。

### 2.3 账号备份与 APK 分析分离

- 账号备份只包含已确认与登录状态、账号列表及切换有关的文件和必要元数据，不备份游戏本体 APK、拆分 APK、原生库或大型资源包，也不修改它们。
- 现有备份工具位于 `F:\Project\07_Androd\16_bakup_tool`，优先用于账号文件采集与前后对比；使用前核对其备份范围，避免沿用整应用备份配置。
- 用户后续提供到 `game-clients/` 的游戏 APK 属于独立的分析输入，不属于账号备份内容。对 APK 的检查以只读分析为原则。
- 后续研究先从 APK 定位原生账号切换入口、方法、接口及调用链，再据此缩小账号文件采集与对比范围，最后验证并实现切换适配。不在本次文档更新中提前开展 APK 分析。
- 定位结果应记录所属模块、类／方法或原生符号（如可识别）、调用条件、参数含义、关联存储及证据位置，并区分客户端内部方法、跨进程接口和网络接口。
- 找到接口名称不代表独立 App 可直接调用；需继续验证入口可达性、进程上下文、权限、会话依赖和实际切换结果，再确定集成方式。

## 3. 使用前提与环境检查

### FR-01 Root 与设备状态

- 首次打开说明 Root 用途，并在用户触发功能时申请 Root。
- 检测实际 Root 命令执行能力，而不仅检查是否安装 Root 管理器。
- 区分未授权、用户拒绝、授权失效、命令失败、目录访问失败等状态。
- 无 Root 时允许查看已保存的非敏感账号元信息；记录受限数据及执行切换入口应展示原因。
- 操作前再次检查授权、剩余空间、目标游戏版本和当前 Android 用户／工作资料空间。
- 首期默认作用于当前 Android 用户；其他用户及工作资料空间不得自动跨空间写入。
- Android 最低版本、目标 SDK、CPU 架构及 Root 管理器兼容清单通过原型测试确定；正式开发前登记，发布前公布。

### FR-02 游戏识别

- 自动识别三款目标游戏，显示名称、图标、包名、版本、安装状态、渠道及适配状态。
- 对未安装、已安装但未适配、已验证支持、版本变更待验证分别显示状态。
- 识别存在歧义时允许选择目标客户端，但不允许仅凭显示名称推断包名。
- 每次游戏更新后重新评估适配范围；未通过兼容检查时停止写入型切换，保留查看及诊断功能。

## 4. 账号状态记录与机制研究

### FR-03 当前状态记录

用户可对指定游戏执行“检测当前账号状态”，形成一次带时间戳的本地记录。

| 记录类别 | 必需内容 |
| --- | --- |
| 环境 | 游戏标识、包名、渠道、版本、Android 版本、用户空间、适配器版本 |
| 账号状态 | 已登录／未登录／待验证／未知；判断依据与可信程度 |
| 账号标识 | 经验证可读取的 UID 或账号标识，默认脱敏；读取不到时支持手动填写 |
| 存储位置 | 实际存在的目录、文件或其他状态载体及用途说明 |
| 文件清单 | 路径、大小、修改时间、摘要、属主、权限及恢复所需的上下文信息 |
| 数据关联 | 文件、数据库、偏好设置及其他状态之间的依赖；哪些需要一并处理 |
| 诊断结果 | 缺失、访问失败、候选项、已确认项及需要进一步验证的项 |

- “发现候选文件”不等于“确认该文件控制账号切换”。界面与报告中必须区分两者。
- 实际账号文件路径、数据库结构、字段、加密方式及会话有效期目前均为待研究项。
- 记录行为默认只读，不主动退出账号、清除数据或覆盖游戏文件。
- 避免直接展示口令、完整令牌及其他可复用登录凭据。

### FR-04 游戏原生切换机制研究

对三款游戏分别建立可复现的研究记录，而不是默认共用同一机制。

研究场景至少包括：未登录、首次登录 A、退出并重启仍为 A、游戏内切换至 B、游戏内退出登录、恢复 A，以及游戏更新后复查。

研究要求：

1. 在用户控制的测试账号和设备上，记录原生账号切换操作及前后状态。
2. 对比必要的本地存储变化，识别账号列表、当前账号选择、会话状态及设备关联信息。
3. 检查是否依赖多个文件、数据库事务、服务状态或服务端验证。
4. 区分“账号已保存”“登录界面已选中”“实际进入目标账号”三个不同结果。
5. 验证切换前是否需要退出或停止游戏，以及何时采集状态才一致。
6. 验证本地状态复现是否足够；如必须执行原生界面流程，则记录所需用户交互及限制。
7. 每项结论提供适用游戏版本、复现步骤、脱敏证据及已知例外。

研究交付物：每款游戏一份机制说明、一份必要状态清单、一份兼容矩阵、一套成功／失败测试记录。只有经过验证的规则才能进入正式适配器。

## 5. 账号保存与切换

### FR-05 保存当前账号

- 在目标游戏完成正常登录后，用户点击“保存当前账号”。
- 检查状态一致性；必要时提示退出并停止游戏后采集，避免读取正在写入的数据。
- 输入账号显示名称和备注，可选填写 UID、标签及排序信息。
- 对必要状态生成独立快照，并记录清单、摘要、游戏版本、适配器版本及创建时间。
- 同一游戏内重复账号应提示“更新已有快照”或“另存”，不静默覆盖。
- 更新快照前保留上一份有效版本；新快照验证通过后才标为可用。
- 保存失败时，不出现可切换的半成品账号条目。

### FR-06 切换账号

标准流程：选择游戏及账号 → 检查兼容性和快照 → 如游戏运行则提示停止 → 记录操作日志并创建当前状态回退点 → 按已验证的原生机制执行必要步骤 → 校验本地结果 → 按设置启动游戏 → 确认目标账号。

- 执行方式由研究结论决定，可以是必要状态恢复、原生流程调用或受控界面交互，不预先绑定单一技术路线。
- 操作前展示目标游戏、账号名称及可能中断游戏的提示。
- 全局一次只允许一个切换事务；切换中禁止重复点击、删除相关账号及并发写入。
- 写入文件时保留或恢复必要的属主、权限与 SELinux 上下文，并按实际环境校验。
- 不采用关闭 SELinux 等全局降级方式解决适配问题。
- 默认不要求备份、移动或重新下载大型游戏资源。
- 支持设置“切换后自动启动游戏”，默认开启。

### FR-07 结果确认、失败恢复与异常中断

- 区分“本地切换完成”“等待游戏验证”“账号切换成功”“失败并已恢复”“恢复失败待处理”。
- 只有通过可靠账号标识确认，或用户在游戏中确认目标账号后，才显示“账号切换成功”；用户确认需标记为人工确认。
- 游戏进程启动成功、命令返回成功或文件摘要一致，均不能单独证明账号已切换。
- 凭据失效或出现验证码时，提示重新登录并更新该账号快照，不循环重试登录。
- 本地步骤失败时尝试恢复操作前状态，并展示恢复结果；本地恢复不承诺撤销已发生的服务端会话变化。
- App 被杀、设备断电或重启后，依据持久化事务记录判断是否存在未完成操作，先处理恢复再允许下一次切换。
- 恢复失败时保留备份及诊断信息，停止进一步写入，提供明确处理说明。

## 6. 账号备注与正常删改

### FR-08 账号列表与详情

- 按游戏分组展示账号卡片：名称、脱敏 UID、备注摘要、标签、快照状态、保存时间及最近切换时间。
- 当前账号状态注明检测时间；最后一次选择的账号不直接等同于当前实际登录账号。
- 支持按名称、备注、UID、标签搜索，支持置顶和手动排序。
- 详情页展示完整备注、状态来源、快照信息、兼容性、最近操作结果。

### FR-09 备注与编辑

- 支持新增、编辑和清空备注；备注允许中文、多行文本及常见符号。
- 建议显示名称 1～40 字符、备注最多 2000 字符；保存前校验，超限不截断用户输入。
- 支持修改显示名称、手动 UID、标签、排序；编辑元信息不改写游戏登录态。
- 账号内部标识与显示名称分离，重命名不影响快照关联。
- 支持单独“重新保存当前登录状态”；元信息编辑与快照替换使用不同入口。

### FR-10 删除

- 支持单账号删除；批量删除列为后续增强项，不阻塞首期。
- 删除前展示游戏、账号名称及数据范围，明确只删除工具内记录和快照，不注销游戏账号。
- 删除不修改游戏当前登录状态，即使被删除条目是当前账号。
- 默认先进入工具内部回收站，保留 7 天；回收期内可恢复，用户可选择立即永久删除。
- 永久删除需二次确认；正在被切换事务引用的数据暂缓删除。
- 回收站及历史快照仍属于敏感数据，遵循相同保护和清理规则。

## 7. 界面与交互要求

### 7.1 页面结构

| 页面 | 主要内容 |
| --- | --- |
| 首页／游戏列表 | 三款游戏卡片、安装及兼容状态、Root 状态、进入账号管理 |
| 游戏账号页 | 当前状态、账号卡片、搜索、保存当前账号、切换入口 |
| 账号详情／编辑 | 名称、UID、备注、标签、快照状态、编辑／更新／删除 |
| 切换进度页 | 当前步骤、目标账号、结果、恢复状态及失败原因 |
| 检测与诊断页 | 脱敏状态清单、适配信息、操作记录及诊断导出 |
| 设置页 | 外观、启动行为、本地保护、备份保留及回收站 |

### 7.2 视觉要求

- 整体采用现代 Android 设计语言，以 Material 3 为默认方向，卡片层次清楚、留白充分、主要按钮突出。
- 支持浅色、深色及跟随系统；三款游戏使用一致布局和适度不同的强调色。
- 账号卡片突出名称、备注及切换按钮，技术信息收纳于详情，不把首页做成文件管理器。
- 完整设计空列表、未安装、Root 拒绝、检测中、切换中、成功、失败及待验证状态。
- 危险操作与主要操作视觉分离，不只依靠颜色表达风险。
- 点击区域原则上不小于 48dp；支持 TalkBack、系统字体放大及长备注换行。
- 动画短而克制，后台任务不阻塞界面；执行途中禁止误操作，但不出现无说明的假死界面。
- 开发前提供关键页面原型；视觉验收至少覆盖明暗主题、小屏及字体放大场景。

## 8. 数据与安全要求

### 8.1 最小数据模型

- 游戏：内部 ID、名称、包名、渠道、签名标识、版本、适配器版本、兼容状态。
- 账号：内部 ID、游戏 ID、显示名称、UID（可空）、备注、标签、排序、置顶状态、时间戳。
- 快照：快照 ID、账号 ID、状态清单、摘要、存储位置、环境信息、验证状态、历史版本关联。
- 事务：事务 ID、目标账号、步骤、前置回退点、结果、恢复状态、脱敏错误信息。
- 密钥和可复用登录凭据不存入普通元信息字段。

### 8.2 本地保护

- 工具保存的账号凭据和快照采用加密存储，密钥优先利用 Android Keystore 管理。
- 加密范围包括快照、临时副本及历史版本；避免在共享存储留下明文凭据。
- 不在日志、通知、剪贴板、崩溃报告中输出密码、完整令牌或原始敏感文件内容。
- 默认排除系统云备份，避免凭据自动迁移；首期不提供跨设备凭据导入导出。
- 诊断导出须由用户主动触发，默认仅含脱敏元信息及错误记录，不包含账号快照。
- Root 环境下的本地加密不代表能抵抗其他已获 Root 权限的软件，产品说明应明确此限制。
- 本地保存、编辑和切换不依赖工具自己的远程服务器；游戏登录本身按游戏网络要求执行。

## 9. 非功能要求

- 可靠性：写入前验证目标范围、状态一致性及回退点；快照损坏或版本不兼容时不尝试盲目恢复。
- 性能：游戏检测、文件读取、加解密及 Root 操作均在后台执行；超过 1 秒的操作显示进度或明确的处理中状态。
- 时延：首期实测确定保存／切换耗时基线，分别统计本地操作和游戏启动登录耗时，不以固定秒数承诺所有设备。
- 存储：展示每个账号快照及总占用；空间不足时在写入前停止，保留已有可用数据。
- 可维护性：三款游戏以独立适配器管理，共用账号 UI、存储、事务和 Root 执行层。
- 可测试性：元信息逻辑可独立测试；真实切换、文件权限及重启恢复必须在真机上验证。
- 可观测性：每次操作有唯一记录、步骤、耗时、结果和脱敏错误；未知状态不得记录为成功。

## 10. 首期验收标准

| 编号 | 验收场景 | 通过条件 |
| --- | --- | --- |
| AC-01 | Root 授权与拒绝 | 授权成功可执行检测；拒绝／失效时无写入，原因明确 |
| AC-02 | 游戏识别 | 三款大陆官方客户端分别识别，包名、版本及适配状态正确 |
| AC-03 | 当前账号记录 | 每款游戏具备真实状态记录、路径／文件清单和判断依据，候选与确认项区分 |
| AC-04 | 原生机制研究 | 每款游戏均有可复现证据、最小状态集合及兼容限制 |
| AC-05 | 多账号保存 | 每款游戏至少保存两个自有测试账号，关闭并重开工具后仍可管理 |
| AC-06 | 双向切换 | 每款游戏 A→B→A 至少连续完成 5 个循环，每次核对实际 UID；记录确认方式 |
| AC-07 | 重启保持 | 重启工具和手机后账号元信息、快照及事务状态保持一致 |
| AC-08 | 备注与编辑 | 多行中文、空备注、重名提示、长度边界、重命名及快照更新行为正确 |
| AC-09 | 删除与恢复 | 删除不注销游戏账号、不改当前登录态；回收与永久删除符合约定 |
| AC-10 | 异常恢复 | 覆盖快照损坏、空间不足、Root 失效、写入中断；失败不冒报成功，可验证恢复结果 |
| AC-11 | 凭据失效 | 提示用户重新登录或完成验证，不自动绕过或无限重试 |
| AC-12 | 版本与渠道隔离 | 不兼容版本、错误包名、不同渠道快照均阻止误写 |
| AC-13 | UI | 明暗主题、空态、进度、错误、小屏及字体放大均无关键遮挡，可完成主要流程 |
| AC-14 | 隐私 | 日志和诊断导出不含可复用凭据；工具不主动上传账号状态 |
| AC-15 | 游戏资源完整性 | 切换不更改无关资源，不触发由工具误操作导致的资源丢失或重新下载 |

测试报告须登记设备型号、系统版本、Root 环境、游戏版本、渠道和适配器版本；结论仅覆盖已测试组合，不扩展为所有安卓设备兼容。

## 11. 实施阶段与阶段出口

1. **机制验证**：先只读检查游戏 APK，定位原生账号切换方法、接口及调用链，再围绕关联账号文件进行最小范围备份、对比与真机验证；先以一款游戏跑通研究方法，再分别完成另两款。出口为三款机制记录及可行性结论，不要求此时完成精美 UI。
2. **最小功能原型**：实现 Root 检测、必要状态记录、两个账号保存、双向切换及恢复；每款独立通过真机验证。
3. **产品化**：补齐备注、编辑、删除／回收、加密、异常事务、搜索及完整界面状态。
4. **首期发布**：三款游戏同时达到验收标准，交付 APK、源码、构建说明、兼容矩阵、测试报告和已知限制。

若某款游戏的登录态受服务端或设备密钥限制，须明确记录受限场景及实际需要的用户交互，不将未经证实的“快照替换成功”当作该游戏已完成适配。

## 12. 待确认与待验证事项

### 产品待确认

- 中国大陆渠道服是否纳入首期，以及具体渠道清单；当前默认先验证大陆官方客户端。

### 技术待验证

- 三款游戏当前版本的真实账号状态位置、必要文件及原生切换流程。
- 会话是否依赖服务端状态、设备密钥或多个客户端共享组件。
- 账号 UID 的可靠读取方式及自动确认能力。
- 必要状态采集时机、恢复权限及更新后的兼容策略。
