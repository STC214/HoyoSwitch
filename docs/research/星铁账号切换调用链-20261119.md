## 1. 修正：combo_widget.account 是下游组件状态

已观察调用链：

```text
WidgetModule.refreshInternal(ACCOUNT_IN)
  → accountChannelInternal().currentAid()/currentMid()/currentCookieToken(callback)
  → WidgetSPUtils.saveAccountData(context, WidgetAccountData)
  → PreferenceUtils.saveString(..., SP_NAME, "account", JSON)
```

- `ACCOUNT_OUT` 事件会清除组件的账号和角色数据。
- `getAccountData` 只从偏好设置取 JSON，再反序列化为 `WidgetAccountData`。
- `saveAccountData` 的已解析静态引用只有 `WidgetModule.refreshInternal` 回调这一处。

**结论：**昨天观察到它随账号变化、且身份匹配数据库是事实；今天代码证明其位于账号模块到桌面组件的下游同步链。它可作为观测信号，但没有证据证明它控制游戏登录，不能以修改它作为切换方案。

证据方法：`WidgetModule.refreshInternal`、`WidgetSPUtils.saveAccountData/getAccountData`；静态引用证据前缀 `ev_10ec1c6f`。

## 2. 原生候选切换入口：Porte LoginManager.loginSwitch

类：`com.mihoyo.platform.account.sdk.login.LoginManager`。

方法显示签名：`loginSwitch(Activity, String aid, ILoginCallback)`。

已观察逻辑：

1. 检查 SDK 应用上下文是否初始化。
2. `PorteAccountManager.getAccount$passport_sdk_release(aid)` 查找已保存账号；找不到则返回账号错误。
3. 通过 `LoginApiService.loginVerify` 发起会话校验，请求使用已有账号状态并要求刷新。
4. 根据服务端结果更新账号对象；可能进入原生验证流程或返回错误。
5. 正常分支经过 `checkSwitchAccountMys$passport_sdk_release`，调用 `saveAccount$passport_sdk_release`，再回调成功。
6. 失效令牌等错误分支可能清理对应 Web 令牌和数据库记录，网络错误不会当作切换成功。

静态入向引用：`com.mihoyo.platform.account.sdk.Porte.loginSwitch`。

**结论：**已定位 SDK 内部的账号选择／校验入口，不是仅修改本地“当前账号”字段。它是进程内方法，不等于另一个 App 可以直接调用的 Android 导出接口。外部可达性、初始化流程和实际运行调用仍待验证；本轮没有重放网络请求。

证据：`LoginManager.loginSwitch`（`ev_f2f76d69`），入向引用（`ev_5f9a863f`）。

## 3. 账号选择、持久化与冷启动候选链

### 3.1 成功保存账号

`PorteAccountManager.saveAccount$passport_sdk_release(account)`：

- 更新账号对象的 `loginTime`。
- `setCurrentAccount$passport_sdk_release(account, true)` 更新静态内存账号，并保存登录状态。
- 通过 `AccountDao.replace(mid, aid, loginType, timestamp, JSON)` 保存账号。
- `replace` 使用 `generateKey(primaryId, loginType)` 构造数据库键，并通过 `CryptoUtils.encrypt` 加密 `data` 后写库。

### 3.2 读取已登录账号

`getLoggedAccount$passport_sdk_release()`：

1. `getLoginStatus()` 为 false 时返回空。
2. 优先使用内存中的 `currentAccount`。
3. 内存为空时，调用 `AccountDao.getLatest$default(...)`，解密并反序列化账号。

`AccountDao.getLatest(includeTapTap)` 按 `timestamp` 排序并取最后一条，且可排除 TapTap 类型；不是按 SQLite `rowid` 直接取最后一条。数据库中的 `data` 需要 `CryptoUtils.decrypt`；解密失败分支可能删除该记录。

`PorteAccountManager.setEnv$passport_sdk_release(env)` 设置偏好文件名为 `porte_sdk_account_` 加环境名；其中的 `login_status` 是此管理器读写的状态。不要与 `mihoyo_sdk_preference.xml` 中同名字段混为一谈。

**推断：**冷启动账号选择至少涉及登录状态、数据库最近账号、加密依赖及后续会话校验。仅改时间戳是否充分、是否还有更上层覆盖行为，尚未实测；不据此执行数据库修改。

证据方法：`saveAccount`、`setCurrentAccount`、`getLoggedAccount`、`getLoginStatus/setLoginStatus`、`setEnv`、`AccountDao.getLatest/replace`，完整名称及 Evidence ID 见 JSON。

## 4. 另一路旧接口：不能与 Porte 路径混用

```text
com.mihoyo.combo.account.AccountModule.setAccount(uid, token, account)
  → channelImpl.setAccount(...)
com.mihoyo.combo.account.MDKCNModule.setAccount(...)
  → MiHoYoSDKProxy.setAutoLoginTokenAndUid(...)
  → com.miHoYo.sdk.platform.module.login.LoginManager.setOldAutoLogin(...)
```

最后一个方法保存 `oldAutoToken/oldAutoUid/oldAutoAccount` 内存字段，在存在 Activity 时将旧自动登录 JSON 写入偏好设置。

**限制：**目前只是追到这一候选旧接口的实现，没有证明昨天的两账号切换使用这一路，也没有证明旧 token 与 `cookieToken` 可互换。后续应优先核对原生游戏实际调用链，避免仅凭方法名称选错入口。

4. 再设计受控的最小状态验证，明确当前状态备份、停止游戏时机、目标账号确认和回退。当前尚不执行恢复、时间戳修改或进程注入。
