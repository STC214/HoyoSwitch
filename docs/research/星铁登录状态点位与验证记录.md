# 星铁登录状态点位与项目进度

更新：2026-11-19，时间均为北京时间（UTC+8）。实测对象：星穹铁道大陆客户端 4.7.0（版本代码 122），包名 `com.miHoYo.hkrpg`，Android 主用户 0。本报告的真机结论仅适用于已测设备和版本；原神、绝区零尚未完成同类验证。

## 1. 结论

- **最可靠的本地状态点位**：Porte 生产环境偏好里的 `login_status`。它是客户端当前会话共用的布尔值，不是每个已保存账号各有一份。A、B 均已登录时读到 `true`，用户清除登录状态后读到 `false`，重开仍是 `false`。
- **同名不等义**：另一份 SDK 偏好也有 `login_status`。在已实测的未登录状态下，它仍是 `true`，即使文件更新也没有跟随 Porte 的标志变化。
- **本地状态不等于认证结果**：单个布尔值不证明服务端会话有效，也不表示用户已进入游戏角色。没有实际修改这个标志，未验证改写后的行为。
- **没有找到独立的「登录中」持久化标志**。静态代码有开始、成功、失败和登出事件，但事件不等于持续状态；不把未找到字段当成字段不存在的证明。

## 3. 真机对比时间线

各行的登录状态由用户手动确认，表格只保留布尔值和修改时间。没有抓取登录凭据或读取日志库内容。

| 采样时间 | 用户确认状态 | Porte 值 / 修改时间 | SDK 同名值 / 修改时间 | H5 日志库修改时间 |
| --- | --- | --- | --- | --- |
| 11:29（基线） | B 已登录 | `true` / 11:20:50 | `true` / 10:42:40 | 11:21:00 |
| 11:48:37 | B → A 后，A 已登录 | `true` / 11:47:51 | `true` / 10:42:40 | 11:47:52 |
| 11:50:43 | 用户已移除所有账号的登录状态 | `false` / 11:49:31 | `true` / 11:49:59 | 11:50:19 |
| 11:52:02 | 关闭并手动重开后仍未登录 | `false` / 11:49:31 | `true` / 11:51:32 | 11:51:42 |

可据此排除两个误判：从 B 切到 A 后布尔值不变，并不代表没切换；未登录时 H5 日志库和 SDK 偏好也会更新，并不代表登录成功。此前另做过官方界面 A ↔ B 双向冷启动测试，重开后都保留了目标账号；那不是第三方文件恢复测试。

## 4. 静态证据如何解读

- `PorteAccountManager.getLoginStatus` 和 `getLoggedAccount` 的静态结果表明，本地标志为 `false` 时 SDK 不返回已登录账号。`true` 只是该检查的一个条件。详见[第一轮 APK 静态分析](星铁账号切换调用链-20261119.md)。
- SDK 区分登录开始、登录成功／失败、登出成功；验证环节通过与整个登录流程成功是两类结果。参考证据前缀：`ev_08d0d0d7`、`ev_6a7a201e`、`ev_9c696b67`。
- H5 遥测相关逻辑有异步写入、达到容量阈值后的清理和上传成功后的删除路径。日志库没有可直接当作当前状态的稳定标志，尚未证明各登录阶段都写进该库。参考证据前缀：`ev_70faa2b7`、`ev_6dee3e81`、`ev_6b24ecf6`、`ev_d38350fc`。

## 5. 实现进度与未完成项

- **自有测试 App**：已安装并使用项目根目录的 `0i.png`。A/B 按钮和「切换后自动打开」开关已加入。自动验收在用户要求接手前验证了 A → B 自动重开并更换进程；新版按钮的关闭开关分支没有跑完自动验收。旧版 ADB 原型的回退验收见[原型说明](../prototype.md)。两种测试都只针对自有 App。
- **真实游戏**：只完成官方界面行为观察、静态分析和布尔值／文件元数据对比。没有实现写入登录标志，也没有将真实游戏登录状态恢复接入测试 App。非 Root 验证中，星铁发行版的 `run-as` 返回 `package not debuggable`；未验证到供第三方 App 使用的恢复入口。

- **签名**：测试 APK 使用本地测试密钥；正式包名、发布证书和密钥管理尚未交付。
- **建议的下一次只读对比**：如用户本来就要重新登录，只记录发起前、等待结果、用户手动确认后三次的布尔值与修改时间。如果过渡太快或两处读数冲突，则记录「未采到／未知」。无需为补样强行退出，也不截图核对账号身份。

## 6. 本地 login_status 开关实验（2026-11-19 13:13–13:14）

本轮首次实际写入该布尔值，用于验证「单改此值能否回到已登录态」。工具与完整用法见[登录状态开关](../tools/登录状态开关.md)。

1. 写入前：游戏未运行，界面停在手机号登录页；Porte 偏好 `login_status=false`，120 字节，SHA-256 `a089179d…`。
2. 停游戏后写入 `true`：文件 119 字节，`ee1d6073…`；属主 10300:10300、权限 660、SELinux 上下文 `u:object_r:app_data_file:s0:c44,c257,c512,c768` 均未变，读回字节一致。
3. 冷启动星铁，等待 14 秒：标志仍为 `true`，mtime 未变，说明客户端启动时没有改写或重置它。同一次启动把 `mihoyo_sdk_preference.xml` 的 mtime 从 11:51:32 推到 13:14:11，其中同名布尔值仍为 `true`，与此前「未登录也会更新」的观察一致。
4. 界面仍为手机号注册／登录、短信验证码与「进入游戏」，未出现「登出」「点击进入」。该次判断依据当场截屏查看，截屏未保存，未进入角色。
5. 停游戏并从备份还原：`false`，120 字节，`a089179d…`，属主／权限／上下文复核一致。

结论：在当前账号数据状态下，把 `login_status` 翻成 `true` 不足以恢复已登录界面。该结果只否定「仅改这一个布尔值即可登录」；不否认证件有效且存在已保存账号时它是返回账号的必要条件，也未验证有效会话下的行为。数据库、令牌文件与 SDK 同名标志均未改动。

副作用与基线变更：Porte 偏好文件修改时间由 13:49 之前的 11:49:31 变为 13:14:42（两次写入）。§3 时间线中该文件以 11:49:31 为基线的时间对比不再适用；布尔值语义仍为 `false`，未登录状态未改变。

## 8. 双向文件级切换验证：B → A → B → A（2026-11-19 13:29–13:39）

- 前提：A 于 13:29 登录，13:30:30 停游戏后拍快照；B 于 13:32 登录，13:33:52 停游戏后拍快照。两份快照均通过 `verify --remote`。
- 差异：A 与 B 只有 4 个文件不同——`porte_sdk_token_PRODUCT.xml`（433 → 816 B）、`mihoyo_sdk_preference.xml`、`combo_widget.xml`（2071 → 2085 B）、`PORTE_ACCOUNT_PRODUCT.db`。`login_status` 两份都是 `true`，不是区分点。
- B → A：13:34:14 把 A 快照写回设备（4 个文件，先自动保存 B 的安全快照），逐文件读回并核对属主／权限／上下文，14 项一致。冷启动后界面为「点击进入」＋「登出」，无重新登录或验证提示；用户目视确认为 A。数据库剩 1 行，`mid`／`aid` 与 A 快照一致，`timestamp` 更新为 13:34:45；`combo_widget.account` 与 A 一致；B 的两行记录消失。
- A → B：13:37:39 恢复 B 快照（安全快照保存 A 状态），4 项写入、14 项校验一致；冷启动 45 秒后为已登录态，用户目视确认为 B。该次未同步做文件层等值核对。
- 回到 A：13:38:53 恢复 A 快照（安全快照保存 B 状态）；冷启动后数据库 1 行且 `mid`／`aid` 与 A 一致，`combo_widget.account` 与 A 一致，用户目视确认为 A。
- 事实补充：客户端在恢复后的首次启动会重写令牌文件、SDK 偏好与数据库 `timestamp`，说明它读取并接受了这套状态，而不是简单丢弃。
- 边界：两次切换用的都是几分钟内刚获得的有效会话；未验证放置较久后的令牌、进入角色后的行为、服务端风控介入、其他版本与两款游戏。本次未改数据库内容，只恢复文件。

## 9. 最小集合验证：4 个文件即可切换（2026-11-19 13:43–13:45）

- 只恢复 A／B 之间实际不同的 4 个文件：`porte_sdk_token_PRODUCT.xml`、`mihoyo_sdk_preference.xml`、`combo_widget.xml`、`PORTE_ACCOUNT_PRODUCT.db`；另外 6 个文件在两份快照之间本来就相同。
- A → B：只写这 4 个文件，冷启动后数据库 2 行且与 B 快照一致、`combo_widget` 与 B 一致，用户目视确认为 B。
- B → A：同样只写这 4 个文件，冷启动后数据库 1 行且与 A 快照一致、`combo_widget` 与 A 一致，用户目视确认为 A。
- 限制：两份快照的 `login_status` 都是 `true`，因此未验证「从未登录状态用这 4 个文件恢复」；也没有继续拆分到更小集合。恢复后首次启动客户端仍会重写令牌、SDK 偏好与数据库 `timestamp`。
